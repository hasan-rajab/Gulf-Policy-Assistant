# NEXUS Assurance Workpapers

These workpapers show how the repository's controls would be documented during a technology-assurance review. Automated results are generated by backend/scripts/run_assurance_review.py; this file does not hard-code pass results.

> Portfolio scope only. No independent audit opinion is expressed.

## WP-AC-01 — Logical access / retrieval authorization

**Risk:** restricted enterprise information is exposed to an unauthorized principal.

**Control objective:** only information authorized for the identity-derived role/department context is eligible for retrieval.

**Control owner in the demo:** application authorization layer.

**Frequency:** per retrieval request.

**Design evidence:** backend/app/core/access.py, backend/app/core/security.py, backend/app/stores/local.py, backend/app/stores/bigquery.py.

**Procedure:**
1. seed public and restricted chunks;
2. execute the same semantic query as an unauthorized principal;
3. confirm the restricted chunk is absent;
4. execute as an authorized HR principal;
5. confirm the restricted chunk is available;
6. inspect implementation to confirm ACL reduction occurs before scoring.

**Expected conclusion:** effective for the deterministic test population if both positive and negative tests behave as designed.

**Production evidence still required:** directory/group source, access-review evidence, joiner/mover/leaver process, sampled access population, privileged-access review.

## WP-ACT-01 — Approval-gated enterprise actions

**Risk:** an AI-assisted request causes an unauthorized or unapproved side effect.

**Control objective:** only allowlisted actions with valid payloads can progress, and execution requires prior human approval.

**Frequency:** per action request.

**Design evidence:** backend/app/services/actions.py and backend/app/services/actions_bigquery.py.

**Procedure:**
1. create a valid action request;
2. attempt execution while status is pending_approval;
3. confirm execution is denied;
4. attempt approval as a non-admin;
5. confirm approval is denied;
6. approve with an authorized independent approver;
7. execute only after approval;
8. inspect audit events for the request, denial, approval, and execution transitions.

**Expected conclusion:** effective for tested transactions if the state machine prevents invalid transitions.

## WP-SOD-01 — Four-eyes / segregation of duties

**Risk:** a privileged requester authorizes their own action.

**Control objective:** requester and approver must be different principals.

**Frequency:** per approval.

**Procedure:**
1. create an action as an administrator;
2. attempt to approve the same action as that administrator;
3. confirm denial;
4. inspect the audit trail for self_approval_prohibited;
5. re-perform using a different authorized approver.

**Exception criterion:** any successful self-approval is a high-severity control exception.

## WP-AUD-01 — Audit integrity

**Risk:** audit evidence is changed after the fact without detection.

**Control objective:** modifications to locally persisted audit events are detectable.

**Design evidence:** backend/app/services/audit.py.

**Procedure:**
1. record normal activity;
2. verify the hash chain;
3. alter a historical row directly in a disposable database;
4. rerun chain verification;
5. confirm tampering is detected.

**Limitation:** tamper-evident local storage is not the same as immutable production retention.

## WP-MON-01 — Audit analytics / exception testing

**Risk:** invalid approval/execution sequences exist without reviewer visibility.

**Control objective:** surface explainable exceptions from structured audit events.

**Procedure:** run backend/app/services/audit_analytics.py over event populations and inspect for:

- SELF_APPROVAL
- EXECUTION_WITHOUT_RECORDED_APPROVAL
- REPEATED_DENIED_LOGIN

**Follow-up:** investigate each exception, determine whether it is a true control failure, document owner/remediation, and re-test.

## WP-CM-01 — Change management quality gates

**Risk:** repository changes bypass security, AI evaluation, frontend, or deployment validation.

**Control objective:** proposed changes are subjected to repeatable automated gates.

**Design evidence:** .github/workflows/ci.yml.

**Procedure:**
1. inspect workflow triggers;
2. confirm backend/security tests run;
3. confirm strict AI evaluation runs;
4. confirm frontend production build runs;
5. confirm deployment/Docker configuration validation runs;
6. confirm executable technology-assurance review runs and produces a CI artifact.

**Residual environment control:** CODEOWNERS and pull-request templates are included, but protected-branch/reviewer enforcement is a GitHub repository setting and is not represented as active unless configured in GitHub.

---

## WP-AI-01 — AI assurance

**Risk:** the model returns unsupported, incorrectly cited, or linguistically inconsistent answers.

**Control objective:** measure retrieval, citation integrity, grounding decisions, supported-language behavior, and adversarial instruction resistance.

**Evidence:** evaluation/eval_set.json, backend/app/services/evaluation.py, .github/workflows/ci.yml, docs/VERIFIED_RESULTS.md.

**Procedure:**
1. ingest the controlled fictional corpus;
2. run the eight-case evaluation;
3. compare actual results to CI thresholds;
4. inspect failed cases rather than averaging them away;
5. retain the CI result as reproducible evidence.

**Limitation:** the suite is intentionally small and cannot support production-accuracy or production-safety claims.
